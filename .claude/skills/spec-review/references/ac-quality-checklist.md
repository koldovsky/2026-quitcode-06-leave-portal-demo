# Чекліст якості вимог і критеріїв приймання (AC)

Кожен пункт — так / ні з посиланням на рядок. «Ні» в пунктах із позначкою **[блокер]** — реліз не тегуємо.

## Кожен AC (`#### Scenario: AC-<AREA>-<NN> …`)

1. **[блокер] Тестований.** Тестувальник, який не бачив коду, однозначно скаже «пройшов / ні».
2. **[блокер] Конкретний.** Числа, дати, межі, коди помилок замість «швидко», «багато», «коректно», «тощо».
3. **[блокер] Один сценарій = один AC.** Один сценарій перевіряє одну поведінку; кілька THEN про різні
   речі — ознака двох AC.
4. **Декларативний.** Бізнес-результат («заявка має статус `pending`»), а не скрипт кліків
   («натиснути кнопку "Зберегти"»).
5. **[блокер] Без реалізації.** Немає назв таблиць, колонок, ендпоінтів, компонентів, бібліотек.
6. **ID за форматом і стабільний.** `AC-<AREA>-<NN>` на початку назви; старі ID не перевикористано;
   змінений AC зберіг свій ID (MODIFIED), видалений — у REMOVED з причиною.
7. **Негативні шляхи.** Для кожної вимоги є хоча б один сценарій помилки або відмови (некоректні дані, чужі дані).
8. **Ролі.** Зрозуміло, від імені якої ролі дія, і що бачать / не бачать інші ролі.

## Кожна вимога (`### Requirement: …`)

9. **[блокер] EARS + SHALL/MUST.** Одне речення: `WHEN …, the system SHALL …` / `IF …, THEN …` /
   `WHILE …, …`; ключове слово англійською, решта — українською.
10. **Назва — це ID.** Перейменування лише через `## RENAMED Requirements`.
11. **MODIFIED** містить повністю скопійований блок вимоги з усіма сценаріями.

## Зміна (proposal.md)

12. **[блокер] Розділи:** Why, What Changes, Capabilities (New / Modified — з шаблону OpenSpec; кожна
    можливість має свою дельту `specs/<capability>/spec.md`), Users & roles, Non-goals, Assumptions,
    Open questions. Impact — необов'язковий (лише вплив на продукт, без коду); його відсутність — не блокер.
13. **Один намір.** Зміну можна описати одним реченням; інакше — розбити.
14. **Non-goals** — справжні виключення (те, що могло б бути метою), а не заперечення.
15. **Open questions** перед релізом: або мають відповідь і внесені у вимоги, або свідомо залишені
    з позначкою, що їх не реалізують у цій версії.
16. **Обмеження платформи враховано:** пошта через вбудований SMTP Supabase (2 листи/год, лише членам
    команди) — не вимога; періодичні задачі на Vercel Hobby — не частіше разу на добу.
17. **[блокер] Анонімізація.** Немає справжніх назв клієнтів, імен, адрес, сум; дані — синтетичні
    (`*@example.test`); `npm run spec:check` зелений.
18. **[блокер] У зміні PM немає `design.md` і `tasks.md`** — це окрема зміна команди `impl-<зріз>` (техлід із розробниками).
