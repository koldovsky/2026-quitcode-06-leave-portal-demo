# 0003. Запрошення — посилання з `generateLink`, а не лист

- Статус: прийнято
- Дата: 2026-10-19
- AC: AC-USERS-01, AC-USERS-02, AC-USERS-04, AC-USERS-05, AC-USERS-11, AC-USERS-14, AC-USERS-15, AC-USERS-17
- Оновлено: 2026-10-19 — пункт 3: сторінка «Активувати акаунт», `verifyOtp` лише в POST (уточнення PM AC-USERS-02, 05)

## Контекст

- PM: адміністратор запрошує людину, а посилання для активації копіює й передає сам (`requirements/01-user-invites.md`,
  Припущення). Вбудований SMTP Supabase — 2 листи/год і лише членам проєкту, тож `inviteUserByEmail` у навчальному
  проєкті не працює для справжніх запрошених.
- Реєстрація в Supabase вимкнена (`enable_signup = false`): з публічним ключем будь-хто інакше зареєструвався б сам.
- Спайк 19.10.2026 на хмарному проєкті демо з `enable_signup = false`: `auth.admin.generateLink({ type: "invite" })`
  створює користувача (профіль — тригер `on_auth_user_created`, роль `employee`) і повертає `properties.hashed_token`;
  `verifyOtp({ type: "invite", token_hash })` дає сесію; повторно те саме посилання — `403 otp_expired`; запрошення
  вже активованої адреси — `422 email_exists`. Запасний шлях `createUser` + `generateLink({ type: "recovery" })` теж
  працює, але не знадобився.

## Рішення

1. Server Action `inviteUser` (`src/app/admin/users/actions.ts`): `getViewer()` (`getClaims()` + роль з `profiles`) →
   не admin — `FORBIDDEN`, admin-клієнт навіть не створюється → перевірки → адреса вже є в `profiles.email` (без
   урахування регістру) — `EMAIL_EXISTS` → **лише тепер** `createAdminClient()` і `generateLink({ type: "invite" })` →
   посада — клієнтом адміністратора під RLS. Порядок закріплено в чистому модулі `src/lib/users/invite.ts`
   (`inviteUserCore`) і юніт-тестах.
2. Посилання будуємо самі: `<origin>/auth/confirm?token_hash=…&type=invite&next=/account/password`. `action_link`
   Supabase не використовуємо — тож Site URL і Redirect URLs проєкту на нього не впливають.
3. `/auth/confirm` — сторінка, а не Route Handler. GET (`src/app/auth/confirm/page.tsx`) лише показує «Активувати
   акаунт» і переносить `token_hash`, `type`, `next` у приховані поля форми — нічого не перевіряє й не витрачає, для
   будь-якого посилання. Server Action `activate` (`src/app/auth/confirm/actions.ts`, POST після натискання): `type`
   лише `invite` або `recovery`; `verifyOtp` → сесія в cookie → `redirect(safeNextPath(next))`; помилка →
   `/login?error=link`. `next` — лише відносний шлях (не `//`, не `/\`, без керівних символів і пробілів, і після
   розбору URL шлях теж не починається з `//` чи `/\`) — захист від open redirect.
4. `/account/password`: `updateUser({ password })` у сесії з посилання; ≥ 8 символів, двічі однаково.
5. Секретний ключ: `src/lib/supabase/admin.ts` — перший рядок `import "server-only"`, єдине місце, що читає
   `SUPABASE_SECRET_KEY`; імпортують лише `actions.ts`/`route.ts`/файли `"use server"` (`npm run check:boundary`, job «Секретний ключ лише
   на сервері»). У Vercel — **лише Production**, не Preview: preview-збірка виконує код будь-якої гілки.

## Розглянуті варіанти

- **`inviteUserByEmail` (лист від Supabase)** — 2 листи/год і лише членам проєкту; власний SMTP — поза
  безкоштовними тарифами курсу.
- **`createUser` з паролем від адміністратора** — пароль знає адміністратор і передає в чаті; людина його не міняє.
- **Відкрита реєстрація + роль за замовчуванням** — будь-хто з публічним ключем стає працівником.
- **Посилання в адресі сторінки (`/admin/users?link=…`)** — credential в історії браузера, логах і Referer;
  тому посилання повертає лише відповідь Server Action.

## Наслідки

- **Посилання = credential.** Хто відкрив його першим, той і задає пароль. Тому: одноразове (повтор — `otp_expired`),
  діє 1 годину (`otp_expiry = 3600`, значення Supabase за замовчуванням), не логуємо, у UI — попередження «передайте
  лише цій людині», після закриття діалогу посилання зникає зі сторінки; на записі екрана — лише одноразовий тестовий
  акаунт, якого потім видаляють.
- **Прев'ю посилань у месенджерах і поштові сканери** відкривають посилання ботом (GET). Перша версія викликала
  `verifyOtp` прямо в GET, і бот «з'їдав» одноразове посилання раніше за людину. Тепер GET лише показує сторінку, а
  токен витрачає натискання «Активувати акаунт» (POST) — так записав і PM (AC-USERS-02, AC-USERS-05, припущення).
- Журнали запитів (`next dev`, Vercel) пишуть шлях `/auth/confirm?token_hash=…`, і тепер — ще до активації, тобто з
  дійсним токеном (до 1 год або до натискання). Доступ до журналів Vercel — лише власник проєкту.
- Відкрите посилання в браузері, де вже хтось увійшов, замінює його сесію — адміністратор перевіряє посилання лише в
  окремому профілі браузера.
- Повторного запрошення ще не активованої адреси немає (відкрите питання PM Q1): `EMAIL_EXISTS` за `profiles.email`.
- Запрошення не атомарне: акаунт створено, а посаду (чи роль) не вдалося призначити — попередження в діалозі,
  адміністратор виправляє в списку.
