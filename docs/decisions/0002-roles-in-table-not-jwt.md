# 0002. Ролі — у таблиці `profiles` + RLS, а не в JWT (Custom Access Token Hook)

- Статус: прийнято
- Дата: 2026-10-19
- AC: AC-USERS-03, AC-USERS-06, AC-USERS-08, AC-USERS-09, AC-USERS-10, AC-USERS-16
- Оновлено: 2026-10-19 — пункт 3: логіку перенесено в `private` (див. «Оновлення» нижче)

## Контекст

- Роль користувача (`employee` | `manager` | `admin`) уже лежить у `public.profiles.role` (міграції WS6); політики RLS
  читають її хелпером `private.current_app_role()` (`security definer`, `search_path = ''`), застосунок — через
  `getViewer()` (`getClaims()` + запит до `profiles`).
- Зріз WS7: адміністратор змінює ролі (AC-USERS-03), не понижує останнього адміністратора (AC-USERS-06), а працівник
  не підвищує собі роль ні сторінкою, ні прямим запитом з публічним ключем (AC-USERS-09). Нова роль — «з наступного
  відкриття сторінки, без повторного входу» (Припущення PM).
- Альтернатива від Supabase — Custom Access Token Hook: функція кладе роль у claims JWT, політики читають
  `auth.jwt() ->> 'user_role'` без запиту до таблиці.

## Рішення

1. Роль — **лише** в `public.profiles.role`. Ніколи з `user_metadata` / `raw_user_meta_data`: їх користувач змінює сам
   (`supabase.auth.updateUser({ data })`).
2. `profiles.role` **без** колонкового grant для `authenticated` (є лише `update (full_name)`). Пастка, яку закриваємо:
   політика `profiles_update_own` («оновлюю свій рядок») + `grant update (role)` = кожен сам робить себе admin.
3. Змінити роль можна лише через `supabase.rpc("admin_set_role", { p_user, p_role })`. Логіка — у
   `private.admin_set_role(p_user uuid, p_role text)` (міграція `20261020000100_admin_set_role_private.sql`):
   `security definer`, `set search_path = ''`; першим оператором — `private.current_app_role() = 'admin'`, інакше
   `42501 FORBIDDEN`; блокування й підрахунок адміністраторів — `23514 LAST_ADMIN`. `public.admin_set_role` — тонка
   обгортка `security invoker`, яка лише викликає приватну функцію. `execute` обох — лише `authenticated`.
4. Server Action `changeRole` викликає `rpc("admin_set_role")` **клієнтом адміністратора** (не admin-клієнтом із
   секретним ключем): `service_role` обходить RLS і перевірки, тож захист жив би лише в коді дії.
5. Тести — PGlite (`tests/db/users-db.test.ts`): відмови працівнику (`UPDATE` і `rpc`), менеджеру, анонімному, останній
   admin. Мутаційна перевірка: без перевірки admin у `private.admin_set_role` червоні рівно AC-USERS-08 і AC-USERS-09
   (відмовні тести повертають ролі у `finally`, тож каскаду на наступні тести немає).

## Розглянуті варіанти

- **Custom Access Token Hook (роль у JWT)** — політики дешевші (без запиту до таблиці), але роль у токені **застаріває**:
  JWT живе до години (`jwt_expiry = 3600`), і пониженій людині права лишаються до оновлення токена, а підвищеній — не
  з'являються (суперечить AC-USERS-03). Потрібні ще хук, його grant-и й примусове оновлення сесії. Повернемось, якщо
  запит ролі стане вузьким місцем.
- **Роль у `user_metadata`** — користувач змінює її сам: ні.
- **`grant update (role)` + політика «лише admin оновлює чужі рядки»** — політика `profiles_update_own` уже пускає
  оновити власний рядок, а колонкові grant-и не розрізняють «свій/чужий»; одна помилка в політиці — і самопідвищення.
  Функція тримає правило (і «останнього admin») в одному місці.
- **Зміна ролі admin-клієнтом у Server Action** — працює, але правило є лише в застосунку; прямий запит до бази його
  не має, а помилка в дії = обхід усіх перевірок.

## Оновлення 2026-10-19

Перша версія (міграція `20261020000000_admin_user_management.sql`) мала логіку прямо в `public.admin_set_role` з
`security definer` — «свідомий виняток» із правила шаблону «definer — лише в `private`». Виняток прибрано новою
міграцією `20261020000100_admin_set_role_private.sql` (застосовані міграції не редагуємо): правило шаблону тепер без
винятків, і демо показує ту саму форму, яку вимагає домашка. Рішення (роль у таблиці, зміна лише функцією бази з
перевіркою admin першим оператором) не змінилось; API застосунку й тести — ті самі.

## Наслідки

- Нова роль діє з наступного запиту: і застосунок (`getViewer`), і політики читають таблицю.
- Кожна сторінка робить запит до `profiles` (ціна — один запит; індекс — первинний ключ).
- Будь-яка нова привілейована дія з ролями — нова функція з тим самим шаблоном (логіка в `private` з перевіркою ролі
  першим оператором, обгортка `security invoker` у `public`), а не новий column grant.
- Міграції в хмарі застосовує власник проєкту (у демо — `npx supabase db push` автором після merge або `db-deploy` з
  секретом `SUPABASE_DB_URL`); до цього зміна ролі на проді відповідає «Не вдалося змінити роль».
